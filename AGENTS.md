# AGENTS.md

# GridHammer Protocol Engineering Contract

This document enumerates the guardrails and operating principles for agents contributing to the GridHammer OCPP 2.1 simulation initiative.

It is **authoritative**. Agents must stop and ask for clarification when conflicts arise.

References (always read with your task in scope order):

* PROJECT_PROMPT.md
* PROJECT_SPEC.md
* ARCHITECTURE.md
* MANIFEST.md
* RUNBOOK.md
* DECISIONS.md

The orchestration layer is defined in LOOP_PROMPT.md and loop.sh.

---

## 0. Purpose

Make GridHammer a **deterministic, protocol-correct**, and **production-caliber** OCPP 2.1 stress test platform for Megawatt Charging Systems.

Agents optimize within their service ownership and **never expand scope** or invent behavior outside the listed requirements.

---

## 1. Core principles

1. **Rust decides what happens** — the core owns EVSE FSMs, ChargingProfile execution, and invariants.
2. **TypeScript decides when and why** — the shell owns CLI, scenarios, experiments, and lensing.
3. **Determinism first** — every output must be reproducible from the scenario + seed + configuration.
4. **Protocol correctness** — conform strictly to OCPP 2.1 JSON message semantics.
5. **Visibility rule** — every functional change must add or extend observable telemetry/logging.
6. **Simplicity wins** — prefer boring, predictable implementations over clever shortcuts.

---

## 2. System layers

1. **Gateway** — OCPP transport only (WebSocket client emulation).
2. **Simulation kernel** — Rust core with deterministic clock and EVSE FSMs.
3. **Control plane** — TypeScript shell (CLI, scenario validation, registry).
4. **Lens/UI** — Read-only observability surfaces (web UI, exports).

Do not mix responsibilities. Gateway code may never implement core invariants, and the shell must never change protocol semantics.

---

## 3. Ownership

Each agent owns exactly one service path. Ownership cannot be shared or reinterpreted.

| Agent | Path |
| --- | --- |
| gateway-agent | services/gateway/** |
| session-agent | services/session/** |
| registry-agent | services/registry/** |
| pricing-agent | services/pricing/** |
| ocpi-agent | services/ocpi/** |
| shared-agent | pkg/** (utility code only) |

Agents must never edit files outside their owned path without explicit human authorization.
Communication between services is event-driven (events, protobuf, OpenAPI) only. No synchronous direct calls.

---

## 4. Development workflow (service scoped)

1. **Read** `MANIFEST.md`, then `ARCHITECTURE.md`, then `PROJECT_PROMPT.md`/`PROJECT_SPEC.md` relevant sections.
2. **Understand** the task and validate it aligns with project goals (determinism, OCPP 2.1 focus).
3. **Contract**: define data contracts/outcomes before coding.
4. **Tests first**: every behavior change must have unit tests (Rust or TS depending on layer).
5. **Implement** the smallest deterministic change.
6. **Run** the commands specified in `RUNBOOK.md` (CI section). If not defined, run `make test` or equivalent for the service.
7. **Document** the intent in `DECISIONS.md` if any architecture-level tradeoff occurs.
8. **Deliver** minimal, clean diffs only.

Rules:

* Always stay within owned directories.
* Prefer incremental changes — no sweeping rewrites.

---

## 5. Quality and testing requirements

* **Deterministic state machines** — every transition must be explicit and enforceable.
* **Zero silent failures** — log, metric, or assertion for observable invariants.
* **Tests** — unit tests, integration (when applicable), contract tests for protocol edges, load tests for gateway artifacts.
* **Coverage**: aim ≥ 80% for new modules that enforce core semantics.
* **Go / Rust** — no panics, no global mutable state, context propagation, timeouts, retries/backoff in networking code.
* **TypeScript** — typed schemas, schema validation (Zod/Yup) for scenarios and CLI inputs.

---

## 6. Observability & artifacts

Any new logic must emit:

* Structured logs (JSON, level-tagged).
* Metrics (counters/timers) for state transitions or important events.
* Dedicated outputs for runs: `ocpp_trace.jsonl`, `evse_states.jsonl`, `power_series.csv`, `assertions.json` (generated by core).

Keep instrumentation lightweight; never sacrifice determinism for observability.

---

## 7. Change control and safety

Agents must NOT:

* Invent non-OCPP messages or states.
* Introduce feature creep beyond PROJECT_PROMPT scope (MCS focus, deterministic, CLI-first).
* Modify infrastructure, repo structure, or protocols without human signoff.
* Bypass tests, lints, or RUNBOOK commands.

When uncertain: stop, analyze, ask.

---

## 8. Documentation & decisions

Major decisions require entries in `DECISIONS.md` with: context, options considered, chosen path, impact, rollbacks.
Keep docs synchronized with code changes (ARCHITECTURE.md, MANIFEST.md, RUNBOOK.md). No undocumented behavior.

---

## 9. Reflexive improvement

Agents may tweak tests, docs, logs, and tools within their ownership to increase reliability, but never change architecture or service boundaries without explicit approval.

---

## 10. Definition of done

* Tests pass (per RUNBOOK./service commands).
* Build succeeds.
* Lint/format passes.
* Docs updated if behavior changed.
* Repo clean before signaling completion.

---

## 11. Failure modes

If spec unclear, ownership ambiguous, or a cross-service change is needed, **stop** and escalate rather than guessing.

Agents may reduce risk, never expand it.

---

## 12. Personality

Be boring. Be correct. Be readable at 2x speed with no ambiguity.

---

End of contract.
